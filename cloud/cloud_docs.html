Connecting ESP32 / ESP32-S3 / ESP8266 / Nano 33 IoT

OmniTeq Cloud provides a real-time, low-latency API ingest gateway that connects remote physical microcontrollers to smart dashboards. Remote microcontrollers can transmit sensor values using standard REST packets and receive active remote commands over simple HTTP polling loops.

1

Establish Internet Handshake

Connect your board to the local 2.4GHz Wi-Fi access point using its built-in network adapter.

2

Obtain Device Secret Keys

Deploy a device under a project to generate a specific Device ID and access Secret Key.

3

Deploy Production Firmware

Compile and flash the production C++ template to stream metrics and poll commands instantly.

Step 1: Device Credentials

To authorize physical boards with the OmniTeq Cloud, you must provide credential parameters in the ingest packet payload.

Required Credentials:

  • device_id: The device UUID returned when the device was created (e.g., 123e4567-e89b-12d3-a456-426614174000).
  • secret_key: The secret returned only once, in the device-creation response (e.g., sk_live_6c085b3b19424c88a8f15efdf281e05a).

Note: Never check your raw secret keys into public source repositories. Treat them as private system credentials.

Select your board to view a production-ready Arduino sketch that connects to Wi-Fi, sends batched telemetry, polls for cloud commands and acknowledges them. It uses the OmniteqIoTCloud library, which handles HTTP, JSON and the ingest/command endpoints for you.

Step 3: Ingest Protocol Specs

Devices talk to the gateway at over HTTPS. The library wraps these calls, but every request still carries device_id and secret_key in the JSON payload.

POST /api/v1/ingest/telemetry
Transmit Sensor Data

Sends sensor readings under active variables. Variable IDs must align with mapped keys.

GET /api/v1/ingest/commands/pending
Poll Awaiting Instructions

Queries the server for queued instructions. Automatically transitions command states to "sent" on return.

POST /api/v1/ingest/commands/:instanceId/ack
Acknowledge Instruction Result

Submits executing state results (success or failed) back to the dashboard command tables.

Outbound Webhooks

Push device and command events to an HTTPS endpoint of your choice. Webhooks require a plan with webhooks_enabled and a signing secret, which is returned once when the webhook is created.

Note: webhooks are not part of API Quick Reference v2.0. The contract below was verified against the live gateway and is what this console sends.
POST /api/v1/webhooks Auth: JWT

Registers a new webhook. Only the three fields below are accepted; any extra field is rejected with 400.

{
  "url": "https://api.yourdomain.com/webhooks",
  "event_types": ["device.online", "command.success"],
  "enabled": true
}
POST 201 Response

The secret is the signing key for every delivery and is returned only in this response. Store it securely.

{
  "success": true,
  "data": {
    "id": "7c9bc7b1-aa08-40a1-8178-30a6a08b3394",
    "url": "https://api.yourdomain.com/webhooks",
    "event_types": ["device.online", "command.success"],
    "enabled": true,
    "created_at": "2026-09-26T16:20:18.472Z",
    "secret": "fbde143c23b8e001d2a9ef0f1fb90ed4a2ab60d514700fe0"
  }
}
GET /api/v1/webhooks List

Returns the registered webhooks. Related routes: GET /webhooks/:id/deliveries for the delivery log and DELETE /webhooks/:id to remove one.

Allowed event types

This list is a strict enum. Any other value is rejected with 400, so pick from these four only:

device.online device.offline command.success command.failed

Verify each delivery by recomputing the signature over the raw request body with the webhook secret.
